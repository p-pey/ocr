# IMPLEMENTATION SPEC — Iranian National Card Birth-Date Reader (machine-oriented handoff)

Audience: an AI coding agent that will finish and harden this project. Read the whole file before
changing anything. Sections 0-3 define the goal and the CURRENT state, sections 4-8 define the design
you must keep, section 9 is the NEW requirement (user-supplied digit shapes) that you must implement,
sections 10-14 are acceptance, tests, risks and the task list.
Keywords: MUST / MUST NOT / SHOULD are normative.

---------------------------------------------------------------------------------------------------
## 0. Product goal (from the user, non-negotiable)

- Input: a photo (any camera / upload) of an Iranian national card (old card and smart card).
- Output: the BIRTH DATE only, Jalali, formatted `YYYY/MM/DD` (Latin digits), plus confidence.
  Nothing else on the card is needed.
- Runtime = browser JavaScript (PWA / WebView, Asanpardakht payments context). Existing runtime
  dependencies: `@techstark/opencv-js` only. Existing UI imports `TesseractOCR` from this module and
  calls `initialize / recognize(imageSrc, onProgress, onAttempt) / terminate`.
- MUST be "ready to use in production without extra process": no prebuild step, no model file to host,
  no language-data download, no Python at runtime, no server. Training happens offline once (by the
  implementer), the result is embedded in the JS bundle as a small base64 weight blob.
- MUST be small and fast: weights <= ~150 KB raw int8; CNN forward ~4M MACs per line crop; whole
  `recognize()` target <= 400 ms desktop / <= 1 s mid-range phone EXCLUDING one-time OpenCV load
  (targets; measure and report real numbers).
- MUST be accurate on digit shapes. The user's key pain: the old OCR (Tesseract `fas`) read the
  Persian zero `۰` (a small DOT) as `۵` or `۹` very often. The user will supply the exact digit
  shapes (section 9). The engine MUST be trained so that a printed `۰` is never confused with `۵`.
- MUST prefer "no answer" over "wrong answer": a wrong birth date on an identity/payment flow is worse
  than asking for a retake. Never guess digits (see 8.3).

## 2. History / decisions you MUST NOT undo (and why)

1. Old engine = tesseract.js `fas` run on every glyph (~33 OCR calls) + geometric hacks. It failed
   (0/5/9 confusion, slow, downloads traineddata at runtime). DO NOT reintroduce Tesseract for digits.
2. A TensorFlow.js version (CNN + tfjs in browser) was built and then REPLACED, because the user wants
   no extra bundle weight / no model hosting. Current inference is hand-written JS in `cnn.js`
   with weights embedded in `modelWeights.js`. DO NOT add tfjs/onnxruntime.
3. Output head design = 8 independent softmax heads (digits YYYYMMDD) + 1 sigmoid `isDate` head.
   Reason: birth date is always zero-padded `YYYY/MM/DD` = exactly 8 digits; no CTC, no per-glyph
   segmentation (segmentation was the old engine's weak point). `isDate` prevents a 10-digit national-ID
   line or a word line from being read as a date. Slashes are not predicted (fixed positions).
   Limitation: dates printed without zero padding (`1375/5/2`) are not supported. If real cards do
   that, the decoder must change (see 12, risk R3).
4. Preprocessing is a CONTRACT shared by training and inference (section 5). Changing it without
   retraining silently destroys accuracy.
5. The engine never "repairs" individual digits by confusion tables or `padStart("0")` guessing.
   It only repairs STRUCTURE (separators, dropped slashes, flipped order) in `dateParse.js`.

## 4. Runtime pipeline (keep this structure)

`TesseractOCR.recognize(imageSrc, onProgress, onAttempt)`:
1. `loadImage` -> `cv.imread` -> `recognizeMat(cv, srcMat, ...)` (DOM-free; used by Node tests).
2. `fitToCard`: downscale to <= 1600 px, Canny + closing + contours, pick largest convex quad with
   area >= 28% of image and aspect 1.25-2.05, perspective-warp to 1200x756 (portrait quad => rotate
   90 deg). If no quad: treat the image as a tight crop (rotate if portrait), scale to width 1200.
3. For rotation in {0, 180} (180 only if rotation 0 produced nothing confident):
   a. grayscale, invert if mean < 110 (dark ink on light paper is what the model is trained on).
   b. `findLineCandidates`: inside `SEARCH_BAND` {x0 .08, y0 .18, x1 .99, y1 .93} -> Gaussian 3x3 ->
      `adaptiveThreshold(GAUSSIAN_C, INV, 31, 12)` -> for kernel widths [13,21,33]: morphological CLOSE
      with (kw x 3) rect -> external contours -> keep boxes with height 18..84 px, width >= 90,
      aspect >= 2.2, width <= 0.9*card width -> pad (0.25h horizontally, 0.3h vertically) -> NMS
      (IoU > 0.6) -> sort by closeness to vertical middle (IDEAL_Y .52) -> top 18.
   c. Each candidate crop -> `grayToModelInput` (section 5) -> `recognizeLines` (CNN).
   d. Keep reads with `dateProb >= 0.6`, valid Jalali date (`parseJalaliDate`, years 1280-1410) and
      `confidence >= 60`.
   e. Test-time augmentation: for the best 4 reads re-read 4 slightly shifted/grown crops
      (`variantRects`), average the 8x10 probability tables (`averageReads`); if the merged read is no
      longer a valid date, multiply confidence by 0.8.
4. Selection (`selectBest`): among reads with confidence >= 85 and dateProb >= 0.8 choose the EARLIEST
   year (the expiry date printed on smart cards is always later than the birth date); otherwise highest
   confidence. If nothing passes thresholds, `best` is `null` (UI shows "retake photo").
5. Result shape (must stay backward compatible with the UI):
   `{ best: attempt+{birthDate} | null, allDates: [...], allAttempts: [...], timingMs }`
   `birthDate = {year, month, day, formatted:'YYYY/MM/DD', raw, confidence(0-100), score, corrected:false, correctionCost:0, votes,...}`
   attempt fields: `strategy, candidateIndex, rotation, rectified, bounds{x,y,width,height as 0-1 fractions},
   engine, rawText, normalizedText, confidence, dateProb, dates[], repairs:0, segmentImages{line}, preprocessedImage`.
6. Always free every `cv.Mat` (`deleteMats`) — leaks crash mobile WebViews.

## 5. PREPROCESSING CONTRACT (training <-> inference, byte-for-byte)

Input to the model: float32 tensor 32 x 160 (H x W), single channel, row-major.
Algorithm (`grayToModelInput` in JS, `resize_for_model` + `standardize` in `training-tools/gen.py`,
`standardize_batch` in `train_keras.py`):
1. Crop of one text line, grayscale uint8, dark ink / light paper.
2. `newW = clamp(round(cropW * 32 / cropH), 8, 160)`.
3. `cv2.resize(crop, (newW, 32), interpolation = INTER_AREA if cropH > 32 else INTER_LINEAR)`.
4. Over the resized region ONLY: `x = (x - mean) / (std + 1e-6)` (population std).
5. Place into a zero tensor 32x160 at columns [0, newW); columns >= newW stay 0 (right padding).
No binarisation, no CLAHE, no sharpening in the recognition path (binarisation drops the small `۰` dot
and is a prime cause of the user's 0/5 problem). Grayscale only.
Any change here requires regenerating data, retraining, re-exporting, and re-running parity tests.

## 6. Model spec

Input [N,32,160,1] NHWC. Layers (Keras, `train_keras.py::build`):
```
conv3x3(1->8)  same, no bias, BN, ReLU, maxpool2   -> 16x80x8
conv3x3(8->16) same, no bias, BN, ReLU, maxpool2   -> 8x40x16
conv3x3(16->32) same, no bias, BN, ReLU, maxpool2  -> 4x20x32
conv3x3(32->32) same, no bias, BN, ReLU            -> 4x20x32
average over height (AveragePooling2D((4,1)))      -> 1x20x32
flatten (index = x*32 + channel)                   -> 640
dropout .3, dense 128 ReLU, dropout .2
head digits: dense 80 -> reshape [8,10] -> softmax (per digit position)
head isDate: dense 1 -> sigmoid
```
~107,897 parameters. Loss = mean over 8 heads of sparse CE (only for samples with isDate=1) + BCE(isDate).
Adam, cosine decay from 2e-3, batch 128, input noise augmentation. You MAY enlarge channels if (and only
if) measured JS speed stays within budget and accuracy gain is shown; `cnn.js` `LAYERS` table and
`export.py` must change together.

Export format (`export.py` -> `modelWeights.js`, read by `cnn.js::loadWeights`):
- BatchNorm folded into conv weights/bias (`s = gamma/sqrt(var+eps)`; `w*=s`; `b = beta - mean*s`).
- Per layer in order [conv1, conv2, conv3, conv4, fc1, digits, isDate] the blob stores:
  all float32 sections first: for each layer `scale[out]` then `bias[out]`; then all int8 sections:
  for each layer the quantised weights. Quantisation: per-output-channel symmetric int8
  (`scale = max|w|/127`).
- Conv weight layout: `[out][ky][kx][in]`. Dense layout: `[out][in]`.
- `MODEL_WEIGHTS_B64` = base64 of the whole blob. (~144 KB base64 for the 8/16/32/32 net.)
`export.py` also writes `out/parity.json` (4 standardised inputs + reference logits) for the JS parity test
(copy to `tests/fixtures/parity.json`). It reports float vs int8 accuracy; quantisation must cost
< 0.3 % absolute exact-match, otherwise use finer quantisation (e.g. float16) and update `cnn.js`.

## 7. Training data — existing generator (`training-tools/gen.py`)

- Fonts: ~360 TTF files extracted from npm packages (vazirmatn, vazir-font, sahel-font, shabnam-font,
  samim-font, tanha-font, parastoo-font, gandom-font, and @fontsource/* Arabic-script families).
  `collect_fonts.py` keeps only fonts whose cmap contains U+06F0..U+06F9 with 10 distinct glyphs.
  Persian digits are rendered from U+06F0..U+06F9 (NOT Arabic-Indic U+0660..0669: shapes of 4/5/6 differ).
  Render with PIL `layout_engine=BASIC`, LTR (digits are BiDi class EN; year is leftmost).
  Some decorative families are excluded (`EXCLUDE`); tanha/gandom/mirza are held out for validation
  ("UNSEEN-fonts" metric = font-generalisation proxy).
  Always eyeball a contact sheet of rendered digits per font before training (some fonts render tofu or
  Arabic-shaped digits).
- Labels: 74 % valid zero-padded Jalali dates (years 1300-1415), 26 % negatives (`isDate=0`):
  10-digit "national id" strings, random digit/slash strings, random Arabic-letter words, blank crops.
  Positive samples sometimes include neighbouring words left/right (label text) in the same crop.
- Crop geometry mimics the engine: tight ink bbox of the main text + random margins
  (0.05-0.8 h horizontally, 0.1-0.6 h vertically), because the engine's blob boxes are padded.
- Augmentation: wavy guilloche lines, low-frequency blobs, illumination gradients, glare, rotation +-3
  deg, shear, perspective, resolution loss (0.3-0.9x), Gaussian/motion blur, contrast/gamma, noise, JPEG.
- Datasets: `gen_data.py N out.npz seed train|held` -> arrays X(uint8 N,32,160) NW(newW) D(N,8) Y(isDate).
  Used: 110k train, 3k val seen-fonts, 3k val unseen-fonts.
- Scene generator `mkcards.py` produces full synthetic photographed cards (perspective, rotation, table,
  blur, glare, JPEG; birth date near the middle, national id below, expiry date at the bottom, label words
  next to values) + `labels.json` with ground truth, for end-to-end engine tests.

Limits of the above: synthetic fonts are NOT the card's printing. Real accuracy is unknown until section 9
(user glyphs) and section 10 (real data) are done. That is the main job.

## 8. Safety / correctness rules in the engine

8.1 Only accept a date if ALL hold: `isDate && dateProb >= 0.6`, valid Jalali (`dateParse`), confidence >= 60.
8.2 Birth date = earliest year among confident valid dates (expiry is later).
8.3 No digit guessing. No confusion-table "repair". No left-padding. Low confidence => `best = null`.
8.4 Provide `minProb` (lowest per-digit winning probability) in attempts; UI may use it to demand a retake.
8.5 Multi-frame use (live camera): the UI should call `recognize` on several frames and accept a date only
    when >= 2 frames agree. SHOULD add a small helper `ConsensusReader` exporting that logic.
8.6 Privacy: never send images anywhere, never log image data / full dates to console in production builds.

## 9. NEW REQUIREMENT — exact digit shapes supplied by the user  (implement this)

The user will provide the ground truth shape of every digit as printed on the card, either as
(A) a PNG glyph sheet, and/or (B) ~10 real birth-date line crops with their known dates. The trained
model MUST reproduce those shapes' identities exactly; in particular `۰` (dot) vs `۵` (loop) must be
separated with a measurable margin.

### 9.1 Inputs to request from the user (ask once, be explicit)
A. `glyph_sheet.png` (one per card generation/font variant, e.g. `glyph_sheet_old.png`,
   `glyph_sheet_smart.png`):
   - black ink on white, a SINGLE ROW typeset in the card's font, in this exact order, left to right:
     `۰ ۱ ۲ ۳ ۴ ۵ ۶ ۷ ۸ ۹ /`
   - glyph height >= 150 px (so downscaling to 18-60 px is clean), >= 20 px blank gap between glyphs,
     all glyphs on ONE common baseline, NOT tight-cropped vertically (the dot-zero must keep its real
     vertical position and size relative to the taller digits). A screenshot of the date line from a
     high-resolution scan, or a vector export, is ideal.
   - If the card uses more than one weight/size, one extra row per variant.
B. `real_crops/` + `labels.csv`: `crop001.png,13750512` — date line crops from real card photos with the
   true date (8 digits, slashes optional). Also include lines that are NOT dates (`crop002.png,none`):
   national-id line, name lines, expiry line labelled with its own date (expiry lines are valid dates
   and are labelled as dates too; the engine disambiguates by year).
   Be honest with the user: 10 crops are enough to verify glyph extraction and as a smoke test, NOT enough to
   claim accuracy. Request >= 200 crops (>= 50 distinct people/cards, varied phones and lighting) for
   validation and fine-tuning; keep 100 % of them out of training for the final report (see 10.3).

### 9.2 Glyph extraction (`training-tools/glyphs.py`, new)
1. Binarise sheet (Otsu), find connected components, cluster components into glyphs by x-overlap/gap
   (digits like `۴` may have several components; `۰` is one small component; do not assume exactly 11
   components). Expect 11 clusters; if not, stop and show the user a labelled contact sheet.
2. HUMAN GATE: render a contact sheet with the assigned label under each extracted glyph and have the user
   confirm the mapping (`0..9,/`) before any training. A wrong mapping poisons the model.
3. For each glyph store: grayscale bitmap (ink alpha), advance box (x-range), baseline offset and height
   relative to the median digit height (the dot-zero should come out ~0.25-0.5 of digit height — verify and
   print the numbers; use them as unit-test assertions: zero height ratio < 0.6, five height ratio > 0.8).
4. Keep a per-variant JSON (`glyphs_<variant>.json`) + PNGs under `training-tools/glyphs/`.

### 9.3 Glyph-based renderer (`gen.py::render_with_glyphs`, new) — THIS BECOMES THE MAIN DATA SOURCE
- Compose date lines `YYYY/MM/DD` (Latin label, Persian glyph shapes from the sheet) by placing glyph bitmaps on
  a shared baseline with realistic advance, jittered spacing (+-8 %), digit height 20-64 px at card scale,
  slight per-glyph scale/rotation jitter (+-3 %, +-2 deg), stroke-weight jitter (dilate/erode +-1 px at card
  scale, plus ink-bleed blur) and keep the dot-zero's real size ratio.
  The `/` glyph from the sheet is used between groups; if missing, derive from a similar font slash.
- Also compose negatives with the SAME glyphs: 10-digit national IDs, random digit strings, `none` crops.
- Data mix for training: >= 60 % user-glyph renders, 25 % other-font renders (robustness), 15 % real crops
  (when available, oversampled x5 and lightly augmented). Run the SAME augmentation pipeline as section 7.
- Hard-negative / confusion focus: oversample strings dense in confusable pairs. Priority pairs:
  `۰/۵`, `۰/۹`, `۱/۷`, `۳/۴`, `۴/۲`, `۶/۹`, `۷/۸`, `۸/۷`. Sample digits with a bias so these appear >= 3x
  their natural rate, including inside real date constraints (month first digit 0/1, day first digit 0-3).
- Low-resolution realism for the dot: include samples where the whole line is downscaled so the dot is only
  ~2-3 px wide (phone photos), plus JPEG/blur. The model must still call it `۰`, never `۵`.

### 9.4 Training
- Same architecture (section 6) unless metrics demand more capacity; train from scratch on the new mix, then
  fine-tune on real crops at lower LR (5e-4 -> 1e-5) with early stopping on a held-out real split.
- Metrics logged per epoch: exact-date accuracy, per-digit accuracy, 10x10 digit confusion matrix on the
  validation set, isDate accuracy; explicitly print the (`۰`->`۵`) and (`۵`->`۰`) confusion rates.
- Keep fonts held-out set for font generalisation, plus a glyph-sheet-variant held-out set if >= 2 variants.

### 9.5 Optional but RECOMMENDED independent verifier (deterministic, no learning) — "shape gate"
Purpose: even if the CNN errs, never silently output `۰` vs `۵` confusions.
- After the CNN reads a candidate line, locate the 8 digit slots in the crop via vertical-projection /
  connected components on the ALREADY-STANDARDISED grayscale (adaptive threshold only for this gate, not for
  the CNN input). For each digit slot compute: height ratio vs the median height of the digit slots, number of
  holes (RETR_CCOMP children), aspect ratio, ink area ratio.
- Rule examples (calibrate numbers from the glyph sheet, section 9.2): CNN says `۰` but slot height ratio > 0.7
  or has a hole => conflict; CNN says `۵` but slot height ratio < 0.55 and no hole => conflict.
- Template check: normalised cross-correlation of the slot against the sheet glyph of the predicted digit,
  multi-scale; require NCC(predicted) >= max NCC(all other digits) - epsilon.
- On any conflict: multiply confidence by 0.5 and set `attempt.gateConflict=true` (=> likely `best=null`).
  Gate must be unit-tested on synthetic images of every confusable pair, and MUST NOT lower accuracy on the
  clean validation set by more than 0.3 % (measure).

## 10. Acceptance criteria (the implementer must produce a written report with these numbers)

10.1 Unit/parity: `node tests/pure.test.mjs` passes, JS-vs-reference max logit diff < 5e-3.
10.2 Synthetic e2e: `mkcards.py` (>= 300 scenes, seen + unseen fonts, plus user-glyph scenes): full-engine exact
     birth-date accuracy >= 97 % on user-glyph scenes, >= 90 % on unseen fonts; wrong-answer rate (confident but
     wrong) <= 0.5 %; remainder must be `best=null`.
10.3 REAL held-out set (>= 200 crops/cards never used in training): exact date >= 97 %, wrong-confident <= 0.5 %,
     `۰`<->`۵` confusion <= 0.2 % per digit instance. If these are not met, report honestly and list the
     failure clusters (lighting, hologram glare, blur, font variant, localisation misses).
10.4 Localisation recall: on real full-card photos, the birth-date line must be among the candidates in >= 98 %
     (log misses; tune `SEARCH_BAND`, kernel widths, thresholds using real cards, NOT guesses).
10.5 Speed (measure, report median/p95, desktop Chrome + a mid-range Android phone): CNN forward per line,
     `recognize()` total excluding OpenCV load; bundle delta of this module (weights + JS) <= 200 KB gzip.
10.6 Memory: run 200 consecutive recognitions in a loop; WASM heap must stay flat (no `cv.Mat` leaks).

## 12. Known risks (decide with data, tell the user)

R1 Real card font/layout differ from synthetic => section 9 + real crops are the mitigation. Accuracy claims
   before that are invalid.
R2 Hologram/guilloche background and glare on smart cards can merge text blobs or hide the dot. Mitigate with
   augmentation from real crops; consider a second candidate finder (MSER / gradient-energy rows) if recall < 98 %.
R3 Dates without zero padding. If real cards show `۱۳۷۵/۵/۲`, replace the 8 fixed heads with 10 character
   slots + CTC (or 12 slots incl. slash/blank class) and update parser/export/JS decode.
R4 `cnn.js` is unproven (see 3). Fix bugs found by the parity test before anything else.
R5 OpenCV.js itself is ~8-10 MB; unavoidable unless card detection + warp + adaptive threshold are reimplemented.
   Do NOT attempt unless the user asks. Optional: lazy-load it and run the whole engine in a Web Worker.
R6 Old-card vs smart-card differences (position of dates, presence of expiry). Calibrate with real samples of both.
R7 Overfitting to the 10 provided samples. Never evaluate on training crops.
